# Production acceptance plan — initial qualification profile

These are release targets, **not measured capacity or claims of current readiness**. Establish and record the actual staging topology before qualification. All final evidence must identify the commit, infrastructure, dataset, concurrency, duration and commands. A supervised pilot is the verdict if any required gate remains unverified.

## Supported first profile

- Private organizations using internal knowledge assistants and approval-controlled automation; 10 workspaces, 100 registered users, 25 concurrent active runs. Workspace is the initial organization isolation boundary; multi-workspace organization administration is not claimed until implemented/tested.
- Two API instances and two workers sharing PostgreSQL with pgvector, Redis and S3-compatible storage. Start qualification with at least 8 total application vCPUs/16 GiB RAM, plus 4 database vCPUs/8 GiB and adequate Redis/object storage. Record actual allocation; do not infer capacity from this proposal.
- Corpus: 5,000 documents / 50,000 chunks across workspaces. Default 15 MiB upload limit, configurable administrator budgets; test actual parser/OCR and duration limits before advertising format support.
- Maximum workflow: 50 nodes, bounded tool/model rounds and a 15-minute active execution budget. Human-wait duration is separately governed; published runs always use frozen revisions.
- Intended data: ordinary business documents authorized by the organization. No healthcare/financial/regulatory certification or arbitrary hostile-code hosting is implied. Public guest use and larger workloads require separate qualification.
- One-hour sustained qualification under target concurrency, with ingestion and provider failure injection; provider charges require authorization. Deterministic HTTP fixture soak measures application behavior, while a separately labeled real-provider sample proves live reasoning/tool/usage behavior.
- Operational target: recovery point <= 1 hour and restoration <= 1 hour, demonstrated from backup. Public availability SLA cannot be inferred from a test run and is not promised by this release.

## Evidence and verdict

Store synthetic test manifests and sanitized summaries under `docs/production/evidence/`; raw sensitive outputs remain private. Each row starts `pending`, then becomes `passed`, `failed`, or `blocked` with a supporting artifact. Passing fixture tests does not pass a live gate. Supplied deployment files do not pass deployment gates until exercised.

Verdicts: **production-ready for the specified profile** only when required gates pass; **supervised company pilot** when bounded known gaps remain; **not ready for company use** when core isolation/durability/security gates fail. The coordinator owns the integrated verdict and must not infer it by adding team feature counts.
