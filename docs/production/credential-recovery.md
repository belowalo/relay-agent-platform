# Credential rotation and recovery

Do these procedures in an isolated staging copy first. Back up the domain database, identity data, object references and **matching vault keyring** before migration. Keep encryption keys in protected runtime/KMS configuration separate from database backups, with recovery access documented for two authorized operators. Do not put key values, bearer tokens, passwords, MFA seeds, reset links or decrypted credentials in logs, command histories, Git, tickets or this handoff.

The foundation vault encrypts with AES-256-GCM and records the key ID. AAD binds workspace, connection and version. `createSecretPort` checks current actor/connection authorization and audits resolution, creation, revocation and key rotation. Revocation denies future resolution; it cannot erase a plaintext credential already in flight. Only trusted connector adapters receive plaintext, and they must bind it to the administrator-configured endpoint using `assertCredentialDestination` and prohibit authenticated redirects.

For key rotation:

1. Add a new random 256-bit key under a unique key ID in the protected keyring. Distribute both old and new keys to all relevant API/worker processes; make the new key active for new writes.
2. With an authorized administrator context, call `SecretPort.rewrap(context,reference,destinationVault)` for each active credential. It locks the row and decrypts/reseals using the **same** reference, so stored run references remain valid. Commit each record atomically, audit it and checkpoint the inventory; retry safely after failure.
3. Rewrap MFA and OIDC verifier envelopes through an offline identity migration using their original references (`identity/userId/1` and `identity/oidc-<state-hash>/1`). Alternatively expire all outstanding OIDC states. Do not silently rewrite a reference or key ID without decrypting and authenticating the original envelope.
4. Verify every active envelope against its reference and new keyring. Test all readers after a process restart and restore a backup in a disposable environment. Compare inventory counts and key IDs without printing ciphertext/plaintext.
5. Retain old keys until old live envelopes and every retained backup that needs them are retired. Key deletion is irreversible for those backups. Remove old keys from runtime only after the inventory is empty and recovery has been rehearsed.

For provider credential rotation, create a new monotonically increasing credential version with `store`; update the connection's current SecretReference through the connector repository and audit it. Decide whether frozen runs may continue using the old version. For compromise, revoke old versions and tokens immediately, block new execution, reconcile in-flight actions and reissue provider credentials upstream. Editing Relay alone does not revoke an upstream API key.

Legacy three-part ciphertext has no tenant AAD. Use `migrateLegacyEnvelope` only in the security-owned import path with the original 32-byte key and a source row whose workspace/connection/version were independently validated. It authenticates the old GCM tag and creates a new versioned envelope; wrong keys or tampering fail generically. Never relabel legacy ciphertext as v1. MFA legacy envelopes need the same explicit transformation. Test restores against both old backup format and new format before retiring the legacy key.

If the database is lost, restore the database and corresponding keyring together, verify membership, revoked token records, credential versions and usage reservations, and rotate browser sessions/reset/MFA challenges/OIDC states out of the restored copy. Restoring an old backup must not reactivate compromised tokens; reconcile revocations against a protected incident record and rotate publication/API credentials. Reconcile queue references and uncertain usage/actions before resuming workers. If the keyring is lost, there is no cryptographic backdoor: restore a protected key backup or replace provider credentials and re-enroll MFA under an authorized recovery procedure.

MFA recovery codes are random, hashed and one-use; disclose the eight codes once and store them offline. Email password reset is single-use, expires in 30 minutes, invalidates sessions and challenges, and **does not disable MFA**. Production account changes require authentication within the previous ten minutes plus password/current MFA as applicable. MFA disable and password changes revoke existing sessions and issue a new one. Organization-required MFA must be re-enrolled before workspace access returns.

For a user without usable MFA/recovery codes, verify identity out of band through the organization's approved operator process. Keep two accountable operator approvals, disable the account and invalidate sessions/challenges first, audit the recovery, remove/reset the MFA envelope and old recovery codes using a narrowly privileged offline identity tool, then require password rotation and enrollment before re-enabling organization access. This branch intentionally exposes no unauthenticated MFA-reset route. Lost owner access or a suspended workspace requires the same protected operator path; there is no public ownership-transfer endpoint.

OIDC: configure HTTPS `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `PUBLIC_ORIGIN`, `COOKIE_SECURE=true`, explicit `OIDC_EMAIL_DOMAINS` and optional `OIDC_CLIENT_SECRET`. Register the exact callback `<PUBLIC_ORIGIN>/api/auth/sso/callback`. Extra discovery endpoint origins need explicit `OIDC_ENDPOINT_ORIGINS`; URLs are still subject to outbound policy. Use code flow with S256 PKCE, one-use browser-bound state and nonce. RS256/ES256/PS256 signatures, issuer, audience/azp, expiry/iat, nonce and verified permitted email are validated. Provision `(issuer,subject)` in the protected identity repository; never link accounts solely by matching email. Production OIDC must use the new async client, not the local auto-provisioning flow. Provider-secret rotation should follow the issuer's overlap/revocation procedure and be tested against the actual provider; only synthetic OIDC/SMTP fixtures were available here.
