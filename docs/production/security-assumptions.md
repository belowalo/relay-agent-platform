# Security assumptions and code audit

This is a security team branch based on foundation `76649286b51b39924261a876878efebf5e02f020`. It supplies tested repositories and enforcement hooks plus fixes to the local HTTP application. It does not qualify the independently developed production system. Existing entrypoints continue to reject `RELAY_PROFILE=production` until runtime composition is implemented. No certification or regulatory-compliance claim is made.

The workspace is the organization boundary. API/worker code, administrator configuration, the migrator, database host, vault keyring and connector adapters are trusted. Workflow input, model output, document content, uploaded filenames, webhook bodies, browser state and serialized job context are untrusted. A tenant context is an internal capability: authenticate its actor before creating it; never accept `{actor,workspaceId}` directly from a request. Compromised privileged database operators, malicious trusted adapters and a compromised runtime host are outside the tenant-isolation guarantee.

Authorization reads current membership/account/workspace/token/resource state. Checks occur at operation boundaries; they are not a distributed lock around an external provider. Removal cannot retract an external request already accepted, erase a credential already decrypted or recall output previously delivered. Runtime must suppress subsequent work/results after revocation and retain accounting/effect reconciliation for accepted work. MFA-required organizations check enrollment as well as identity authentication; prohibit alternate login paths that skip the MFA challenge.

The integration omissions above are material release blockers, not a claim that the entire platform is secure.

## Shared outbound-request policy

Import `safeFetch`, `responseText`, `checkURL`, `assertCredentialDestination` and `createOutboundPolicy` from `server/network.js`. Every provider, connector, crawler, embedding/reranking endpoint, tool, OIDC endpoint and webhook callback must use the shared adapter. Do not use bare fetch/axios/SDK defaults, caller-provided dispatchers or unchecked follow-up/SSE URLs. SDKs need an injected fetch using this adapter. `checkURL` alone is insufficient because a later independent request can resolve DNS again.

Default public calls:

```js
const response = await safeFetch(endpoint, { signal, noRedirect: true });
const data = JSON.parse(await responseText(response, 200000));
```

For deliberately approved private integrations, create a capability once from protected deployment/administrator configuration, never from workflow/request/job JSON:

```js
const internalPolicy = createOutboundPolicy({
  origins: ['https://search.internal.example:8443'],
  privateCidrs: ['10.42.8.0/24'],
});
const response = await safeFetch(configuredEndpoint, { signal, noRedirect: true }, internalPolicy);
```

Both the origin (scheme/host/port) and resolved address must match. Limit exceptions to the required network segment; prohibit broad ranges in deployment review. Link-local, `100.100.100.200` and `fd00:ec2::254` are hard-denied; include provider-specific metadata addresses in the infrastructure firewall. A policy is a private-network exception, not a public-domain allowlist: enforce provider endpoint allowlists separately where required. HTTP is supported for deliberate private integrations; use TLS/mTLS when credentials are involved. `ALLOW_PRIVATE_NETWORK`/boolean exceptions remain local-only compatibility features.

Bind a credential to its configured endpoint with `assertCredentialDestination` before resolving plaintext. Authenticated requests must set `noRedirect:true`; check all SDK-generated destination URLs. Do not include tokens in URLs. Read bodies through a byte limit or use a streaming adapter with explicit byte/event/time/cancellation limits. Dispose/cancel unused bodies. Non-HTTP protocols require an independently reviewed adapter and cannot inherit this policy implicitly.

## Database and deployment assumptions

Apply append-only migration `0200-security.sql` after the foundation. Its security workspace registry must be provisioned/imported alongside authoritative runtime workspaces; missing rows deny access. Runtime/connector/knowledge rows need their own tenant RLS and validated domain references. These modules do not grant database privileges automatically. Use dedicated non-owner, non-superuser, non-BYPASSRLS roles; assert the application role at startup. See the permission document for column-level identity access and append-only audit grants.

Keys come from protected deployment/KMS configuration, never generated silently during production startup. The keyring and privileged recovery credentials are separate from database backups. No secrets or live service credentials were used in these tests. Run the live security service harness on a disposable PostgreSQL database, the foundation PostgreSQL/Redis tests, real issuer/SMTP tests and combined runtime/knowledge/connector/load acceptance before production enablement.
