# SQLite to PostgreSQL migration

Never test on the active application database. First rehearse these steps using synthetic representative fixtures or an authorized disposable backup. This import is explicit and atomic; it does not convert the running SQLite process in place.

1. Quiesce the SQLite application and workers. Create a consistent SQLite backup with the SQLite backup API or `VACUUM INTO` on an authorized copy; do not copy the main file while WAL writes continue. Keep the original database, associated legacy vault key/encryption key, binary files and deployment configuration privately backed up. Rehearse restoring that complete backup. Do not put backups or keys in this repository/worktree.
2. Provision an empty disposable PostgreSQL database with pgvector and a migrator role. Set MIGRATION_DATABASE_URL privately, run `npm run foundation:migrate`. Provision restricted roles following the runtime operating guide.
3. Set target `ENCRYPTION_KEY` and `ENCRYPTION_KEY_ID` privately, matching the production vault. Run `npm run runtime:import -- --source <absolute-backup.sqlite> --legacy-key-file <private-vault.key>`. Default is dry-run; it exercises the complete integrated import, integrity, foreign keys, shipped SQLite migration version 9, tenant references, credential/MFA decryption and rewrap, and an empty destination. It emits only row counts, file SHA-256, compatibility summary and number of halted active runs. It refuses a source with a WAL file.
4. Review counts and backup identity, then repeat with `--apply`. One pinned PostgreSQL transaction and advisory lock imports all domain tables, preserves IDs/domain JSON, rewraps credentials and MFA under the target vault's authenticated envelopes, adds derived workspace scope, reconstructs run event sequences and resets imported leases. Ciphertext changes during rewrap; plaintext is never emitted. A populated destination is rejected. A failure rolls back all imported rows. The migration does not blindly rewrite SQLite SQL or import FTS shadow tables; knowledge must rebuild search/vector indexes.
5. Validate account/membership counts, graph/revision/run relationships, credential resolution through the security adapter, documents/blob references through knowledge/connectors, and frozen application publication data. The integrated synthetic PostgreSQL rehearsal verifies rollback/apply, source SHA preservation, restricted ACLs, session revocation, credential resolution/AAD boundaries and overwrite refusal. Restore is separately exercised by the deployed backup drill. Your organization's representative authorized data rehearsal is still required before cutover.
6. Legacy active runs and schedules have no saved authorized runtime actor and remain halted. Inspect external actions and pending approvals before creating new authorized execution. Import maps legacy completed actions to succeeded and ambiguous legacy write states to uncertain. Legacy approvals are preserved for audit; they do not automatically grant a new runtime approval. Do not fabricate a service actor to resume imported pending actions. Security owns legacy credential rewrap; ciphertext is never relabeled as a new envelope.
7. Start production API/workers only after the domain ports, identity, accounting, shared binary storage and model/tool adapters are composed. Exercise a supervised synthetic workflow, approval, cancellation and restart. Keep the original SQLite backup immutable for rollback. PostgreSQL writes after cutover are not automatically reverse-migrated; rollback requires an explicit reconciliation/export plan and review of any remote effects.

Dry-run inserts into the destination inside the same validated import transaction and then rolls it back. It tests destination constraints and rewrapping without committing records. A committed apply/restore rehearsal on a disposable target remains mandatory. Do not apply into an existing partially populated database or retry by deleting arbitrary rows; restore/recreate the disposable target and repeat validation.

The integrated importer preserves restricted source ACLs and fails on unknown or empty restricted policies. It rejects vectors that are not 384-dimensional; compatible old vectors require reindexing when their embedding model differs. Sessions, invitations and old publication grants are revoked. Legacy memories with unknown writer provenance are preserved but quarantined from execution. Assign provenance only after an authorized review. Binary blobs must be moved to verified shared object storage separately; preserving references does not copy files. The original application database and key are never modified by qualification.

The current offline importer materializes source rows in memory. Provision sufficient private migration-host memory for the backup, and rehearse corpus-sized imports before cutover. Binary files and embedding/search reindexing are separate domain migration steps; this command preserves references and serialized embedding records, not shared-object-store contents or a qualified retrieval index.
