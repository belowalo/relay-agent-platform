# Permission matrix and organization boundary

The workspace is the initial organization boundary. There is no implicit multi-workspace organization administrator. The executable matrix is `server/security/authorization.js`; unknown roles, permissions, missing identities, suspended workspaces, expired grants and missing resources fail closed.

| Operation                                           | Viewer | Editor | Administrator | Owner                     | API application / worker service                    |
| --------------------------------------------------- | ------ | ------ | ------------- | ------------------------- | --------------------------------------------------- |
| Workspace, workflows, runs, documents: read         | Yes    | Yes    | Yes           | Yes                       | Explicit permission and resource grant only         |
| Workflows/documents: create or change               | No     | Yes    | Yes           | Yes                       | No application-token management permission          |
| Run, retry, cancel, review exact approval           | No     | Yes    | Yes           | Yes                       | Execute/read only; never a model-generated reviewer |
| Invoke connector / resolve connection credential    | No     | Yes    | Yes           | Yes                       | Explicit connection grant and current policy        |
| Manage credentials, tokens, publications, workspace | No     | No     | Yes           | Yes                       | No                                                  |
| Invite/manage viewers and editors                   | No     | No     | Yes           | Yes                       | No                                                  |
| Invite/manage administrators                        | No     | No     | No            | Yes                       | No                                                  |
| Change/remove owner                                 | No     | No     | No            | No through membership API | No                                                  |
| Audit read                                          | No     | No     | Yes           | Yes                       | No                                                  |
| Budget changes / organization MFA and domain policy | No     | No     | No            | Yes                       | No                                                  |

Restricted document ACLs apply to every role, including owner. There is no implicit administrator ACL bypass. Resource lookup must return an authoritative `{workspaceId, access?, applicationId?, disabled?, revoked?}` row; document access is `{mode:'workspace'|'restricted', principalIds:[...]}`. This implementation uses typed principals such as `user:<id>`, `application:<token-id>`, `service:<grant-id>`; see the handoff proposal because v1 did not freeze principal encoding. Filter candidates **before** embeddings/reranking, snippets, counts, citation serialization or database tools. Revalidate ACLs when showing saved evidence and exported runs; possession of an old run ID is not document authorization.

Application context `actor.id` identifies a scoped token grant, not a caller-supplied application ID. A token has an application association, explicit permissions, explicit resource references, expiry of at most 90 days, hashed bearer credential and revocation timestamp. A run may inherit access through an application grant only when its authoritative `applicationId` matches that token's application. Tokens lose validity when their issuing administrator is removed, disabled or demoted. Rotation revokes the old token and creates the replacement in one transaction.

Browser session permissions and API permissions are separate. Browser cookies do not authenticate `/api/apps` calls. Public guest access may invoke only an explicitly public application and read its own run using an opaque receipt. It cannot list workspace resources or access the detailed API/event stream. Private metadata requires a token. The local implementation now requires a per-run HttpOnly receipt cookie; the production runtime must preserve this boundary with a durable guest repository.

Every route needs the relevant permission **and** a scoped resource lookup. Apply the same rules to component tests, retry, downloads, SSE reconnects, evaluations, schedules, child workflows and connector synchronization. Each child inherits the originating actor; a frozen graph or queued job does not freeze authorization. Service grants must be administrator-approved persisted records, never fabricated from job JSON. Sensitive actions use current membership/token/resource policy before external work and before secret resolution. An already accepted external action remains an in-flight action when membership changes.

Invitations are email-bound, seven-day, hashed, one-use and revocable. Acceptance rechecks the inviter's current role, workspace suspension and domain policy. An existing membership is never upgraded by accepting an invitation. Role changes/removal invalidate outstanding invitations and tokens issued by the affected member. Owners cannot be demoted or removed through these methods. Enabling organization-required MFA requires an owner already enrolled in MFA; recovery access must be preserved first.

Database roles are a second boundary. The application role gets workspace repositories through forced RLS and `SELECT(id,email,disabled_at,mfa_enabled)` on accounts, never password hashes or MFA ciphertext. The identity role gets only global identity/session/challenge repositories. The rate-limit role gets only rate buckets. Grant `INSERT,SELECT` on audit tables to normal roles, never UPDATE/DELETE. Migrator/backup roles are privileged and require separate protected credentials. Production startup must call `DatabasePort.assertApplicationRole()`.
